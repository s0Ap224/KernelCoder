# KernelCoder 的下一步：验证、版本管理与代码审查

下一阶段的目标：先让一个小任务具备“能验证、能恢复、能解释完成依据”的完整流程，再扩充工具。KernelCoder 已经有执行和隔离的基础，接下来最有价值的是把这些基础组织成可验证的开发过程。

## 一、建立能记录证据的验证流程

先不急着增加很多工具。bash 已经能运行测试，缺的是对验证结果的管理。例如为一次改动记录：

```json
{
  "command": "python -m pytest tests/test_login.py -q",
  "exit_code": 0,
  "status": "passed",
  "revision": "本次被验证代码的版本标识"
}
```

关键是把验证结果绑定到代码版本：**测试通过后又修改了相关代码，旧的通过记录就不能直接证明新版本正确。**

流程可以是：

```text
确定验收条件 → 修改 → 运行相关检查
                         ↓
                    失败则修复
                         ↓
                 检查通过或明确报告阻塞
```

还要区分“测试失败”“环境缺依赖”“没有测试”“没有运行”。这些状态不能都由模型一句“完成了”带过。

对于 bug 修复，最好增加能复现原问题的测试，并确认修改前失败、修改后通过；再运行相关既有测试，检查是否引入回归。修复循环也要有次数或预算上限，避免一直改下去。

## 二、把单文件撤销升级为任务级版本管理

当前 checkpoint 更像：

```text
撤销刚才对某个文件的一次修改
```

希望实现的回溯则是：

```text
恢复到这次任务开始前
恢复到上一次验证通过的版本
```

这需要记录一组文件的完整状态，包括新增、修改和删除。可以基于当前 sandbox 的基线、快照机制继续扩展，也可以结合 Git 分支或 worktree。

重点不是加一个 `git reset` 命令，而是明确：

- 任务开始时的基线是什么。
- 用户原本未提交的修改如何保留。
- 哪个版本通过了哪些检查。
- 恢复时会影响哪些文件。

文件快照也只能恢复其覆盖的文件，不能自动撤销安装依赖、外部服务写入等所有副作用。

## 三、把“实现”和“审查”分成两个阶段

完成修改后，给审查阶段提供：

```text
用户需求 + 实际 diff + 相关代码 + 测试结果
```

要求它检查具体问题：需求遗漏、边界条件、错误处理、兼容性、测试是否真正覆盖了问题。

可以使用一次独立的模型调用，后续再考虑专门的 reviewer Agent。独立上下文有助于从不同角度检查，但模型审查仍然需要测试和人工判断配合。
